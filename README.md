# vadimohka.ru

Личный сайт Вадима Владымцева. Статические HTML, CSS и JavaScript; публикация из `main` через GitHub Pages.

## Структура

- `index.html` — главная.
- `background/`, `projects/`, `approach/`, `context/` — путь, проекты, подход и материалы.
- `essays/` — архив и шесть самостоятельных эссе; `essays/feed.xml` — RSS.
- `assets/` — действующие стили, скрипт навигации, утверждённый портрет и иллюстрации эссе.
- `favicon.ico`, `favicon.svg`, `apple-touch-icon.png` — иконки.
- `llm/` — текстовые HTML-версии двенадцати страниц.
- `index.html.md` рядом с каждой основной страницей — её Markdown-версия.
- `llms.txt`, `llms-full.txt`, `*/llms.txt`, `person.jsonld`, `llm-profile.json`, `sitemap.xml` — навигация и данные для поиска.
- `.well-known/ai-catalog.json`, `.well-known/ard.json` — два генерируемых каталога одних и тех же публичных материалов.
- `scripts/` — генерация альтернативных форматов, проверки и исходный авторский текст.
- `en/` — совместимость старых адресов английской версии. Не удалять.
- `CNAME`, `.nojekyll`, `robots.txt`, `yandex_98b0fe03a0ad0233.html` — настройки публикации и подтверждение сайта.

## Изменение содержания

Редактируйте основные HTML-страницы: это источник видимого текста, заголовков, описаний и дат содержательных изменений. Авторский текст страницы «Подход» хранится в `scripts/content/approach.md`; проверка сверяет с ним текст, ссылки и метаданные. Правила редактуры — в [scripts/COPY.md](scripts/COPY.md).

Исходные сведения о человеке и организации находятся в `scripts/data/profile.json`. Опубликованный `person.jsonld` — результат генерации; его больше не редактируют как исходник. Если меняется факт, повторённый в видимом тексте, обновите соответствующий HTML. Проверки сохраняют согласованность роли, контакта, источников и стадий проектов.

Маршруты, подписи страниц и набор ресурсов описаны в `scripts/site_model.py`. Генератор, альтернативные представления, каталоги и сборка используют этот общий реестр.

Генератор работает на стандартной библиотеке Python 3.10+. Полный набор проверок использует Python 3.11+ и закреплённые зависимости JSON Schema; CI запускается на Python 3.12. Однократная подготовка окружения:

```sh
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -r scripts/requirements-validation.txt
```

После правок из корня репозитория выполните:

```sh
python3 scripts/sync-discovery.py --write
bash scripts/validate-seo.sh
```

Генератор обновляет метаданные, Markdown, LLM-страницы, индексы, RSS, sitemap и оба каталога. Он не переписывает видимый текст основных страниц. `dateModified` берётся из JSON-LD страницы: меняйте его при содержательной правке, а не при каждой сборке.

Альтернативные представления должны быть закоммичены вместе с исходными страницами. Их нельзя удалять как дубликаты: они публикуются на сайте. Проверка `--check` выявляет расхождения с исходными HTML. Независимый валидатор также проверяет canonical, ссылки между основным HTML, Markdown и текстовой версией, а также навигацию корневого и страничных `llms.txt`.

Для локального просмотра:

```sh
python3 -m http.server 8000
```

## Эссе

Каждое эссе публикуется по постоянному адресу `/essays/<slug>/`. Тезис стоит в первом абзаце, контекст объясняется внутри текста. Ссылки на другие эссе, сведения об авторе и приглашение к разговору находятся за пределами основного текста. Раздел работает без JavaScript, а общий скрипт сайта управляет только мобильным меню.

Редактируйте `essays/<slug>/index.html`. Полный текст находится в `#essay-body`: первый абзац — `.essay-thesis`, остальные — `.essay-prose`. Из этого контейнера генерируются `Article.articleBody` и `wordCount`. Не редактируйте Markdown, RSS или JSON-LD `Article` вручную. Заголовок, описание и даты принадлежат исходному HTML: `datePublished` и `dateModified` задаются в узле `#webpage`, а видимая дата публикации — в `time.essay-date`. При содержательной правке меняйте только `dateModified`; дату первой публикации сохраняйте.

Чтобы добавить эссе, создайте HTML по образцу существующего, добавьте его в `ESSAY_SPECS` и соответствующий набор поисковых запросов в `scripts/site_model.py`, а затем карточку в `essays/index.html`. В карточке укажите ту же дату, что в статье, включая русскую подпись. Размещайте карточки по убыванию дат публикации: их порядок определяет порядок `ItemList` и RSS. Независимая проверка сверяет даты, подписи и хронологию, даже если производные файлы согласованы между собой. Дополните независимый перечень эссе в контрольном HTTP-клиенте и его регрессионных проверках. Выполните генерацию, проверки и сборку, перечисленные ниже.

В sitemap входят только основные HTML-адреса. Текстовые HTML-копии имеют canonical на основную статью и `noindex`; Markdown и scoped `llms.txt` обнаруживаются через ссылки в `<head>` и общие индексы. Архив получает `CollectionPage` и `ItemList`, эссе — `WebPage` и связанный `Article` с автором, датами и полным текстом. BreadcrumbList отражает путь «Главная → Эссе → статья».

Иллюстрации нового эссе находятся в `assets/essays/helping-startups-grow/`: две картинки WebP и три векторные схемы с отдельными мобильными версиями. `<picture>` выбирает вертикальную компоновку схем на экранах до 600 px. Для каждого изображения заданы размеры и содержательный alt. Обложка статьи согласована в Open Graph, Twitter, `WebPage.primaryImageOfPage`, `Article.image` и sitemap; изображение `Person` остаётся портретом автора. Новые публичные картинки нужно явно добавлять в `FIXED_FILES` упаковщика.

RSS содержит заголовки, описания, постоянные ссылки и даты публикации. Даты с точностью до дня передаются через `dc:date` в формате `YYYY-MM-DD` и namespace `http://purl.org/dc/elements/1.1/`. Это сохраняет точность редакционного источника; необязательный `pubDate`, требующий времени и часового пояса, не выдумывается. Проверка обнаруживает отсутствующую, дублированную или неверную дату, лишнее время и неверный namespace. Для передачи RSS допускаются `application/rss+xml` и стандартные XML-типы. Наличие разметки, Markdown и каталогов обеспечивает техническую доступность материалов; индексацию, позиции в поиске или цитирование внешними моделями оно не гарантирует.

## Публикация и обслуживание

`.github/workflows/static.yml` публикует только `main`; ручной запуск из другой ветки также не допускает публикацию. В Pages остаются пять шагов: checkout, упаковка публичных файлов, configure, upload и deploy. Установка зависимостей, SEO-проверки, тесты, HTTP-клиент и проверки опубликованного сайта в этот workflow не входят.

`scripts/package-site.py` копирует в `dist` только файлы из общего явного перечня `public_files()` в `scripts/build-site.py`. Упаковщик работает на стандартной библиотеке Python и не вызывает сборку с проверками. В сайт не попадают исходники инструментов, схемы, зависимости, документация сопровождения и отчёты проверок. Повторить упаковку локально:

```sh
python3 scripts/package-site.py
```

Независимый `.github/workflows/seo.yml` проверяет изменения в рабочих ветках и pull request, собирает сайт и запускает контрольного HTTP-клиента; его также можно запустить вручную. Для этих проверок `scripts/build-site.py` сохраняет служебный inventory отдельно в `_dist/inventory.json`: пути, допустимые HTTP Content-Type, размер и SHA-256 каждого ресурса.

```sh
python3 scripts/build-site.py
python3 scripts/check-discovery-client.py --serve-dir dist --report _dist/discovery-trace.json
```

При изменении генераторов, проверок или доставки выполните также регрессионные проверки; независимый CI запускает их для рабочих веток и pull request:

```sh
python3 scripts/test-discovery.py
python3 scripts/test-discovery-client.py
python3 scripts/test-delivery.py
```

Контрольный клиент запускает временный сервер на `127.0.0.1`, начинает с главной страницы и находит каталоги по `<link>` в `<head>`. Затем получает тринадцать ресурсов — всего шестнадцать HTTP-документов с главной страницей и двумя каталогами — и проверяет доступность сведений для восьми сценариев: личность и роль, опыт, Belka, Multiverse, подход, подтверждающие источники, контакт и навигация, полные авторские эссе. Он не импортирует генератор. Адреса источников сравниваются с полными целями Markdown-ссылок; пять шагов подхода должны иметь разные номера и пояснения; каждое эссе должно обнаруживаться через архив и содержать полный текст с авторством. Отчёт показывает фактически прочитанные URL, типы ответов и контрольные суммы. При ошибке он сохраняет причину и уже выполненную часть проверки, а при сбое HTTP — также неудачный запрос; CI сохраняет готовую сборку и трассировку даже при сбое клиента. Эти проверки подтверждают обнаружение и наличие доказательств; качество ответа конкретной LLM и включение во внешний реестр проверяются отдельно.

Для отдельной ручной проверки опубликованного сайта `scripts/check-live-discovery.py` использует inventory и сверяет GET-ответы обычных публичных URL со сборкой. Для HTTP-запросов нужен `curl`. Проверяются типы содержимого, JSON/XML и контрольные суммы. Предыдущая версия файла и временные ошибки допускают повтор в пределах общего срока ожидания. Ответ HTML вместо JSON или неверный тип ресурса останавливают проверку. Копия сборки для сравнения включает скрытый каталог `.well-known`; `CNAME` и `.nojekyll` проверяются как файлы упаковки.

Контрольного клиента на каноническом домене также можно запустить вручную. Эти команды сохраняют отчёты локально в `_live/`; при сбое доставки видны уже проверенные и ещё ожидающие ресурсы:

```sh
python3 scripts/check-live-discovery.py --inventory _dist/inventory.json --artifact-dir dist --report _live/delivery-report.json
python3 scripts/check-discovery-client.py --base-url https://vadimohka.ru/ --report _live/discovery-trace.json
```

Для восстановления версии верните проблемное изменение через обычный revert, повторите генерацию и проверки и опубликуйте исправленный `main` штатным workflow. Каталоги и связанные документы должны восстанавливаться одним согласованным изменением. История Git и артефакты независимого CI позволяют сопоставить версию с результатами проверки.

AI Catalog и ARD формируются отдельными экспортами общей модели. ARD добавляет контекст и поисковые запросы. Заголовки и описания страниц берутся из редакционного HTML. Идентификаторы сохраняются при обычном редактировании документа; `https://vadimohka.ru/#person` продолжает обозначать человека, а URN каталога — ресурс.

На двенадцати основных и двенадцати текстовых страницах генерируются relations `ai-catalog` и `ard`; ссылки есть также в корневом и scoped `llms.txt`. Для AI Catalog HTML указывает семантический тип `application/ai-catalog+json`; статический сервер может возвращать допустимый `application/json`. Эта совместимость проверяется отдельно от формата самих документов.

Правила закреплены в `scripts/schemas/` с указанием первичных источников, версий и лицензий. ARD проверяется по официальной JSON Schema целого manifest (`#/$defs/ArdManifest`). Проверка AI Catalog использует локальное структурное описание на основе нормативного CDDL; оно не выдаётся за официальную JSON Schema или универсальную реализацию CDDL. Сборка не загружает изменяемые схемы из сети.

Чтобы добавить материал:

1. Создайте или обновите исходную HTML-страницу и зарегистрируйте маршрут в `PAGE_SPECS`, если он новый.
2. Для включения в каталоги добавьте `ResourceSpec` с постоянным ID, реальным путём, типом и осмысленными поисковыми запросами. Проверьте, нужен ли новому материалу отдельный сценарий контрольного клиента. Обычные правки текста не требуют новой записи.
3. Выполните генерацию, полный набор проверок, сборку и контрольный HTTP-проход.
4. Закоммитьте исходники и все изменённые производные файлы вместе.

Текущие записи описывают документы. Установка skill или вызов API требуют существующего артефакта, понятного способа использования и отдельной проверки поддерживающего клиента перед включением в каталог. В каталоги не добавляют обещания будущих возможностей или дополнительные факты, отсутствующие в публичном содержании.

## Ресурсы репозитория

В `assets/` оставляйте только используемые ресурсы. Новые runtime assets и файлы подтверждения сайта добавляйте в `FIXED_FILES` внутри `scripts/build-site.py`; страницы и зарегистрированные ресурсы каталогов включаются из общей модели. Проверка ссылок в собранном дереве обнаруживает забытые локальные файлы. Перед удалением проверяйте ссылки в HTML, CSS, JavaScript, структурированных данных и скриптах. Сохраняйте основной портрет `assets/hero-vadim-2026.webp` без замены или повторного сжатия.

Не коммитьте кэши, локальные окружения, отчёты браузерных проверок и каталоги сборки. `.gitignore` содержит правила для этих файлов. Устаревшие версии доступны в истории Git; архивные теги прежних рабочих веток не являются действующими ветками.
